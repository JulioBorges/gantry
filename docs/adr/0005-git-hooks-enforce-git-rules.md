# Git-level rules are enforced by git hooks; harness hooks only guard the guards

Rules about git operations — no force push, no commit that skips or weakens a test — are enforced where the operation is visible as an operation, not as a string: in the repository's own `pre-push` and `pre-commit` hooks. `pre-push` rejects any non-fast-forward update by checking `git merge-base --is-ancestor <remote-sha> <local-sha>` for each ref it receives on stdin, which is the definition of a force push and covers `--force`, `-f`, combined short flags, `+refspec`, `--mirror` and `--force-with-lease` without recognising any of them. `pre-commit` rejects a commit whose staged diff (`git diff --cached`, honouring the `GIT_INDEX_FILE` git sets for pathspec and `--include` commits) introduces a test-skip pattern, which covers `-a`, pathspecs, `-i`, `git stage` and every other way content reaches the index. Both hooks print one denial line, on stderr only, naming the rule and the path, and append `hook.denied` to the run log through `runlog.py`. Recording is guaranteed, not best-effort: a git hook inherits the environment of whatever shelled out to `git`, which no harness controls, so the Run is resolved by `runlog.resolve_hook_run` — `GANTRY_RUN_ID` (and, for an isolated state root, `GANTRY_STATE_ROOT`) when the caller does export them, otherwise the *current-Run marker* the round workflow writes into the worktree's own git directory (`runlog.py mark <run-id> --cwd <worktree>`, read back by `runlog.py current`, cleared by `runlog.py unmark` when the Run ends). `reference/round-workflow.md` marks the repository root at the start of every round and each Issue worktree as it is assigned, before any agent works there, so every operation an agent performs inside a Run happens in a marked worktree. Git keeps one git directory per worktree, so the marker is keyed per worktree by construction and concurrent worktrees of one execution unit never attribute a denial to each other's Run. Outside a Run there is no Run log to write to, and the denial still refuses the operation. `pre-push` additionally scans what a fast-forward push introduces (the remote's tip, or the parent of the oldest commit the push adds) for the same test-skip patterns, because `git commit -n` is git's own short `--no-verify` and skips `pre-commit` entirely; the push is the next point where git shows the content itself instead of a command string. They ship tracked under `.agents/skills/gantry/hooks/git/` and are activated by `core.hooksPath`, which `gantry-setup` writes as part of the repository's hook decisions; worktrees share them through the common directory. The harness-level guard (`guard.py`) keeps protecting `ROADMAP.md` and Issue `Status:`/checkbox fields on `Edit`, `Write` and `MultiEdit` payloads — those are paths, not shell — and its only remaining Bash rule is a linear substring check that refuses a command carrying `--no-verify`, `--git-dir`, `GIT_DIR=`, `GIT_CONFIG=`/`GIT_CONFIG_` or, case-insensitively (git configuration keys are), `core.hookspath`, because those disable the git layer. It tokenises nothing, so a 1 MB payload is answered in a few milliseconds, and it allows every other Bash command — including `-n`, which is unremarkable in `head -n` or `sort -n` and is caught at the push instead: git decides. ADR-0003 stands unchanged — hooks at both layers block shortcuts and record; neither grants readiness or completion — and a harness without hooks still relies on the prompts and the Critic, as the spec already requires.

## Considered options

- **Recognise the git operation in the Bash command string** (regex, then `shlex`). This was the design of `gantry-migration#09` through three implementation rounds and three adversarial refutations. Each round closed one spelling and opened another: quoted separators inside `-m` hiding a trailing `-a`, pathspec and `--include` commits, `git stage`, combined short flags (`-uf`), quoted refspecs (`'+main:main'`), `--mirror`, token literals (`git 'push'`), absolute paths (`/usr/bin/git`), `git -c`, and `sh -c '…'`. Shell is an open language and a blocklist over it never converges; the regexes were also quadratic on 1 MB payloads (25 KB = 0.5 s, 100 KB = 7.8 s, 1 MB > 60 s), and full `shlex` tokenisation of 1 MB in CPython is itself close to the 200 ms budget.
- **Narrow the spec to best-effort detection of listed shapes.** Honest, and cheap, but it leaves a real gap the Critic can point at forever and turns a guard into a lint.
- **Give `guard.py` a time budget that fails open with `hook.degraded`.** Necessary hygiene for any hook, but it addresses latency, not the bypasses, so alone it changes nothing about enforcement.
- **Enforce in git hooks and reduce the harness guard to protecting them** (chosen). The hook sees the actual ref update or index content, so spelling is irrelevant and cost is proportional to the diff, not the command. The residual risk — an agent constructing `--no-verify` or a `core.hooksPath` override in a way no substring reveals — is far smaller than the current surface and is bounded by the fact that the harness's Bash tool is the agent's only entry point. The cost is a real setup step (`core.hooksPath`), which already belongs to `gantry-setup`.
- **Recording the denial: exported environment variable vs. a worktree marker.** Exporting `GANTRY_RUN_ID` from the round workflow into every subagent invocation was considered and rejected as insufficient on its own: the harness-neutral `agent()` contract carries a label, phase, model and cwd, not an environment, and even where a harness could inject one, the variable would have to survive every shell the agent opens before it reaches `git`. The marker inverts the dependency — the hook reads state attached to the place the operation happens, which git itself keys per worktree — and the exported variable remains an accepted override for callers that do have one.
