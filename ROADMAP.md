# Roadmap

Delivery tracking for the Gantry skill pack. Two layers:

1. **Specs** — the hand-written sequence below: which spec comes next, what it depends on, why it is in
   that position. One spec is planned and executed at a time, after the operator approves its slicing.
2. **Issues** — one checkbox per implementation issue, grouped into **execution waves** computed from the
   blocker graph (wave N only depends on waves below N, so each wave is one round of parallel
   implementation, one `/asdlc wave:N` run). This layer is generated; the spec layer is not.

**Each issue's `Status:` line is authoritative for that issue.** The generated blocks are a projection of the
issue files, regenerated by `python3 .agents/skills/asdlc/scripts/roadmap.py`. When the two disagree, the
issue wins and this file is stale — regenerate it.

- Specs: `.scratch/<slug>/spec.md` (living-specs template, validated by the pack's structural check)
- Issues: `.scratch/<slug>/issues/NN-<slug>.md`
- Vocabulary: `CONTEXT.md` · Requirements: `PRD.md` · Decisions: `docs/adr/`

## How to update this file

When an issue is completed, run `roadmap.py done <spec#NN>`. It ticks the issue's acceptance criteria,
sets `Status: done`, ticks the checkbox here and refreshes every counter in one pass. `roadmap.py check`
reports any drift and must be clean.

When a blocker changes or an issue is added, run `roadmap.py waves`: the wave layout is derived from the
blocker graph and is never edited by hand. The script refuses a graph with a cycle.

The **Specs** table below is edited by hand, and only by the operator: a spec moves to *planned* when its
`spec.md` exists and passes the structural check, to *approved* when the operator approves its slicing,
and to *done* when every one of its issues is done.

Do not tick an item here without setting `Status: done` in the issue, and do not tick an item whose
acceptance criteria are not all met. A partially delivered slice stays unticked.
